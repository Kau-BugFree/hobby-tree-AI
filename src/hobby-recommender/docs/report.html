01 / DESIGN INTENT

가능한 활동을 남긴 뒤,
잘 맞는 취미의 순서를 정합니다.

기존 onboarding.ts의 질문 키·선택지·단독 선택 규칙을 보존해 API 요청에 연결했습니다. 원본의 initial은 Figma 예시 선택 상태이므로 사용자 답변으로 자동 전송하지 않습니다. 예시 추천 카드의 96·92 같은 숫자도 실제 추천 계산에 재사용하지 않습니다.

A / 설명 가능성

결과에 계산 근거를 붙입니다.

각 질문의 적합도, 가중치, 기여 점수와 추천 이유를 함께 반환합니다. 점수는 0~100 범위의 설계값이며 개인의 만족 확률이나 정확도는 아닙니다.

B / 데이터 분리

규칙을 코드 밖에서 관리합니다.

질문·가중치·활동 카탈로그를 별도 JSON으로 관리하고 버전을 응답에 남깁니다. API·입력 모델·추천 서비스가 분리되어 취미 추가와 검증을 독립적으로 진행할 수 있습니다.

취미를 시작하지 않겠다는 답도 하나의 정상적인 결과입니다.Q01에서 시작 의사가 없거나 Q11에서 직접 찾기를 선택하면 browse를 반환합니다. 답변을 모두 채워야만 추천받는 구조가 아니며, 누락은 자동으로 무관심이나 0원으로 바뀌지 않습니다.

03 / RANKING MODEL

단순하게 계산하고,
가중치의 의미를 드러냅니다.

Score(h) = Σ weight(q) × fit(q, h)

fit은 0~1 · 가중치의 합은 100 · 최종 결과는 0~100점

관심 40목적 30물품 10장소 15동행 5
  1. 응답을 정해진 형태로 읽습니다.

    단일 선택은 문자열, 복수 선택은 배열입니다. 실제 선택한 값만 전송하고, 미응답 그룹은 생략합니다.

  2. 여러 선택을 하나의 적합도로 합칩니다.

    Q03 목적은 평균을 사용합니다. 다른 점수 질문은 최댓값을 사용해 관련 물건을 여러 개 선택했다고 점수가 중복으로 늘지 않게 합니다.

  3. 모르는 답은 0.5로 둡니다.

    미응답, ‘아직 모르겠어요’, ‘상관없어요’ 등 별도 점수가 없는 선택은 중립값 0.5입니다. 미지원 관심사만 선택해도 세 취미를 모두 중립으로 평가합니다.

  4. 가중 합산 후 남은 취미를 정렬합니다.

    지원 취미 직접 선택은 그 취미 1.0, 다른 취미 0.5입니다. 직접 고른 여러 취미에는 각각 1.0을 적용합니다. 점수 동률은 hobby_id 오름차순으로 정렬해 같은 입력에서 결과가 바뀌지 않게 합니다.

50점은 ‘반반의 확률’이 아닙니다.아무런 순위 신호가 없으면 세 취미 모두 50점이 됩니다. 이때는 응답 충실도와 추가 확인 질문을 함께 읽어야 합니다. 가중치를 바꾸기 전에는 사용자 만족도·첫 활동 선택·완료율로 검증해야 합니다.

활동별 확인 완료를 저장하는 기능은 아직 없습니다.카탈로그의 checks는 항상 확인 항목으로 반환합니다. 모든 물품을 true로 보내도 요리·악기는 재료·작업·연주 소리 조건를 앱에서 별도로 확인해야 합니다. 최상위 follow_up_questions는 추천 취미별 첫 활동의 확인 목록만 모으므로 다른 활동을 고르면 해당 활동의 confirmation_required를 읽어야 합니다.

응답을 읽는 순서

  1. status와 버전을 확인합니다.

    설문·규칙·카탈로그 버전을 묶어서 저장하면 동일 조건의 결과를 비교하기 쉽습니다.

  2. recommendations 안의 취미와 활동을 표시합니다.

    hobby_id는 서버의 안정적인 식별자입니다. MVP ui_key는 ‘요리’·‘악기’·‘독서’입니다. 엔진 코드는 Spring의 숫자 DB ID와 구분합니다. score 뒤에 %를 붙이지 않습니다.

  3. breakdown으로 점수를 설명합니다.

    질문 키, 가중치, 적합도, 기여 점수, 답변 여부와 선택값을 보여 줍니다. 응답 충실도 coverage는 점수의 신뢰 확률과 구분합니다.

  4. 제외·미지원·추가 확인을 숨기지 않습니다.

    excluded, unsupported_interests, notices, follow_up_questions를 적절히 안내합니다. preferences의 기록·부담 설정은 화면에 별도로 반영합니다.

동점은 hobby_id 오름차순입니다. weighted_answer_coverage는 점수표에 있는 선택지가 하나 이상 존재하는 질문들의 가중치 합(0~100)입니다. 커피만 선택한 Q02는 포함되지 않습니다. answered_groups는 비어 있지 않은 응답 그룹 수이며 ‘아직 모르겠어요’도 포함합니다. 활동은 eligible 우선 → 첫 비용 → 전체 시간 → 활동 ID 순으로 정렬합니다.

오류 응답과 재시도

입력 검증 실패는 HTTP 422, 추천 계산 중 예상하지 못한 예외는 500, 추천 서비스가 준비되지 않았거나 사용할 수 없으면 503을 반환합니다. 500·503 응답은 {"detail": "안내 메시지"} 형식이며 내부 예외는 서버 로그에만 남깁니다. 서비스가 없으면 상태 확인·카탈로그·설문 조회도 503입니다. 잘못된 설정 파일은 기존대로 서버 시작을 실패시킵니다.

RecommendationApiError.status로 분기하고 500·503의 message를 안내에 사용합니다. retryable은 HTTP 5xx에서 참이며 재시도 시점은 앱에서 결정합니다. HTML·일반 텍스트·빈 오류 응답도 상태 코드를 유지하고, 네트워크 실패·호출 취소는 기존 예외로 전달합니다.

컨테이너 실행
